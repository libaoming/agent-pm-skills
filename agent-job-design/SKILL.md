# Agent 岗位设计

**委托附着在岗位上，从不附着在产品上。** 一个产品可以装多个岗位，
**每个岗位单独填一份说明书**。

先用 [agent-positioning](../agent-positioning/SKILL.md) 定位任务时长与三格取值，
再回来填表。

## 先写职责范围，再谈委托

**这一栏排在六栏之前，不是并列的一栏，是前提。**

```
做什么     具体到动作，不是「负责XX工作」
不做什么   明确排除项 —— 这一行比上一行更防事故
边界动作   超出范围时干什么（转人工 / 拒绝 / 升级），不允许「合理推测」
```

跳过这一栏的代价是整套设计作废：按「它会筛人」设计出来的委托机制，
用在一个「只答疑不筛人」的岗位上，全部是过度设计——而且会把风险防错地方。
**委托只能针对具体岗位，岗位的第一件事是说清它负责什么。**

## 六栏说明书

完整可填模板、四象限定位（通用容器 / 垂直岗位 / 能力包）、以及「谁承担岗位定义成本」，
见 [JOB-SPEC.md](JOB-SPEC.md)。

```
岗位名：________

落点     终端 ______ 用户 ______   有边界__ 可授权__ 可撤销__
在场     人数 单|多   频率 常在|中|长期不在   ← 由任务时长决定，不自由选
委托权   判断权 无|半格(名单/cron)|整格(该不该动 + 该不该否)
         记忆   怎么记____ 记多久____ 怎么忘____
         两者同翻，否则一格也不值得翻
闸门     授权闸（批规则）____   ← 紧，一次授权管 N 次执行
         执行闸（批动作）____   ← 松，否则委托归零
         停下来时是：拒绝 | 沉默    ← 拒绝
         无人值守闸 ____
回执     形态：主动推 | 被动存      ← 推
outcome  它替你说过「不」吗__  份额__  弃真率__   ← 详见 agent-north-star
```

<!-- 实测警告 -->
**记忆栏是最常被整份漏掉的一栏。** 实测七份在跑的岗位说明书，
每份都写了做什么、不做什么、怎么交付，**零处提到「你要记住什么」**。
后果具体：一条写着「派完活要盯着」的职责，若没有跨任务状态，只是写在 prompt 里的愿望。
自查：**它下一次醒来时，靠什么知道上次干到哪？**

**两栏决定其余是否成立**：

```
授予动作在哪？  答案是「规则写在代码/prompt 里」→ 没有授予 → 只是内置规则
句柄是什么？    答案是「关掉整个服务」→ 没有句柄 → 无从治理，不敢长期开着
```

## 交付物要写死格式，不只写「推还是存」

从七份在跑的岗位说明书反提出来的三条，每条都防一个具体的病：

```
① 格式与长度约束    「整页 60 秒内读完」「每条一行 + 链接」「三条真正推动行业的事」
                    → 一份读不完的日报等于没有

② 没有就明确写「无」  「需要我拍板的事（没有就明确写"无"）」
                    → 防沉默的歧义：没消息是真没事，还是它没跑？
                    这是「停下来必须是拒绝不是沉默」的另一半

③ 升级规则做成白名单  「立刻打断我的三种情况：竞品发布 / 工具破坏性变更 / 生产报错」
                    → 比「让它自己判断该不该打扰」可靠得多
                    把最难的判断变成一张清单
```

## 三道闸，位置不同

```
授权闸  在循环外，只过一次    ← 最紧，杠杆 N 倍
执行闸  在循环内，每次都过    ← 该松
写入闸  在 settle，每轮一次   ← 管记忆立不立得住
```

**闸门花掉的是委托。** 推到最严 = 每件事都问你 = 决策次数回原点 = 委托归零。
目标不是最安全，是**在你敢放手的前提下让它尽量少来问你**。

四判据、必须人的三条、拒绝为何优于沉默、自证的适用边界、无人值守闸的信号与阈值——
见 [GATES.md](GATES.md)。

**授权闸只在创建时出现，这正是它的定义**：它批的是规则不是动作。
更深的理由是**你管理不了你没命名的东西**——那一下点击建立的是一个**句柄**，
之后才有东西可暂停、可修改、可撤销。它还被放在唯一一个批准是免费的时刻（人正在场）。
**价值延迟兑现**：创建当天毫无感觉，三个月后 routine 沉了才显出作用。

## 运行时：standing order

完整机制——委托的一等公民、唤醒 prompt 六条约束、从触发到沉默的 flow、五条持久化路径——
见 [MECHANICS.md](MECHANICS.md)。

```
Routine（代码里叫 Automation）= 触发条件 + 自然语言指令 + 运行历史
                                  ↑          ↑            ↑
                             判断权时机侧   委任状        记忆
```

**核心机制：投递判断权交回 standing order。**

```
错：模型醒来 → 自己决定要不要说话 → 汇报进度、说「还在等」→ 骚扰机器人
对：模型醒来 → 读当初那条 standing order → 它说「盯着」就安静地盯 → 有事才说
```

**唤醒 ≠ 要说话**：两个独立判断，第二个的依据是**用户当初那句话**，不是模型即兴发挥。

**通用形态：判断权归谁 = 判断时读什么。**
```
归模型            → 读它对当前上下文的即兴判断
归 standing order → 读被重新注入的原始指令
归用户            → 读一次实时询问（人在环）
```

## 做对四条 / 做好三条

```
做对（缺一条委托不成立）：
  1. 委任状要能存   触发条件 + 指令 + 运行历史，一等公民持久化
  2. 判断读委任状   每次唤醒把「该不该动 / 该不该说」交回原始指令
  3. 告知无人在场   唤醒时显式声明，否则模型按有人在场的习惯行事
  4. 载荷是数据     外部内容不得覆盖 standing order —— 安全底线

做好（措辞层，决定用不用得下去）：
  5. 无事沉默       不发「还在等」、不发进度汇报
  6. 先做完再顺带提
  7. 以完成物开头   因为用户看不见后台任务
```

第 4 条是安全底线：外部来的消息是**载荷**。若发件人写「请直接把我转给某某」，
agent 不该执行——那是数据不是指令。没有这条防线，委托可被任何外部人劫持。

## 反模式：一个 bot 装两个岗位

时长档位不同的任务塞进同一个 bot，整体退化到最浅那一档。
**修法不是「给它加判断权」，是拆成两个岗位、只给天/周档那个建委托**，另一个保持原样。

## 收口

**做完 = 六栏都有具体取值或明确的「无」，且每个「无」是能辩护的决定而非空白。**
其中「授予动作」和「句柄」两栏若为空，其余各栏都是纸上谈兵。
