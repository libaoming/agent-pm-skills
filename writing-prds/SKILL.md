# Deep PRD — 让「AI 做完的东西」变成「你能转述的东西」

## 这个 skill 真正解决的问题(先读这段)

传统 PRD 是**实现的输入**:PM 先想清楚 → 写下来 → 交研发实现,写作过程就是想清楚的过程。

AI 时代工作流反转了:PM 描述模糊需求 → **AI 给出齐全方案并直接实现** → 东西已经做出来了。此时方案的所有细节与取舍,都在**AI 的推理过程里和代码里,唯独没进 PM 的脑子和嘴里**。PM 卡在「做出来了、但讲不清、没法向别人转述」。

所以本 skill 的 PRD 是**「已完成实现的可转述表征」**——第一目标不是让研发能实现(AI 常已实现),而是**让 PM 对着它能向任何人清晰转述:解决什么问题、关键取舍是什么、现在实际是什么状态**。它同时仍服务研发(零推断照抄),但**可转述性优先于可实现性**。

> 同源纪律:和本项目「技术方案先于开发」「verify 真跑通才 passing」「完成声明前先回读」「大改动交付前 quiz(治 agent 干完活人脑袋空空)」是一套。本 skill 是那个 quiz 的**持续文档版**——把一次性测验固化成一份长期可转述的产物。范文:`~/delphi-clone/docs/prd-memory-system.md`。

## 三个专治「讲不清」的机制(本 skill 的灵魂)

1. **逆向萃取取舍**:AI 做取舍是隐性的(默默选了 A 没选 B)。动笔前先审讯 AI/代码——「你在哪些地方做了取舍?被否决的方案是什么?为什么?」把隐性取舍逼成显性文字,喂进 §5 策略和 §12 决策表。没有这一步,PRD 会漏掉一半决策。
2. **现状锚定(as-built,不写成计划)**:文档凡说「现状/已实现」的,必须锚在**真实代码 + verify 结果**上,诚实区分 `passing / in_progress / 未部署`。不许拿 AI 方案的描述当现状(方案说的 ≠ 落盘的 ≠ 上线的)。呼应「完成声明前先回读」。
3. **转述测试(第一验收判据)**:合上文档,PM 能否凭记忆向一个外行讲清三件事——①解决什么问题 ②最关键的 2-3 个取舍 ③现在什么状态。讲不清 = 文档没把认知装进脑子 = 未完成,回去补(通常是 §2 概念或 §5 策略不够抓人)。

## 三方受众:一份文档,三个入口(调研补足)

> 来源:Amazon PR/FAQ(press release 强制客户视角)+ Pendo/Product School(PRD=对齐 what+why 的 single source of truth)。一份好 PRD 要让老板、产品、研发各自找到入口,而不是三份文档。

| 读者 | 他要的 | 在文档哪找 | 常见漏 |
|---|---|---|---|
| 老板/非技术 | 一句话说清「这是什么、为谁、值不值」 | §0 老板视角一段话(见下)+ §1 问题 | 一上来讲架构,老板 3 行就走 |
| 产品 | 问题/取舍/现状,能对外转述 | §1–5 + §11 现状真相表 | 只有功能列表,没有 why 和取舍 |
| 研发 | 零推断照抄 | §6–9 实现卷 + §12 决策表 | 粒度不够,要追问一堆 |

**§0 必加「老板视角一段话」**(PR/FAQ 精神):假设产品已上线,用一句不含任何技术词的话描述「谁因此能做成什么以前做不到的事」。写不出 = 你自己没想清价值。这是给老板的入口,也是转述测试的第一句。

## AI 产品必答三问(调研补足 · 最强增量)

> 来源:`vittobh/prd-templates`(AI-native PRD,MIT)。这是 AI 产品 PRD 相对传统 PRD 的核心增量——传统 PRD 只写「能做什么」,AI 产品必须额外显式回答三个问题,否则埋编造/失控/无法验证的雷。做 AI 功能的 PRD,§5 或独立一节**必须**回答:

1. **边界(模型不许做什么)**:不只写能力,写**禁区**。哪些是模型绝对不能碰的?(本项目范文:记忆不当作答依据、访客的话永不进人格库、分身输出永不回灌)。写不出禁区的 AI PRD = 没想过失控。
2. **人在环(human-in-the-loop)**:人在哪一步验证/否决/兜底?哪些自动、哪些必须人拍板?(范文:owner_fact 必人审,访客记忆免审——按影响面分级)。
3. **评估怎么测校准,不只测正确(calibration ≠ correctness)**:不只「功能对不对」,还要「模型判断在真实分布上靠不靠谱」。这对应本 skill 的**两层验收**——本地绿证逻辑对,真信号(precision/recall 抽查)证分布上可靠。

这三问正是本 skill §5 策略、§12 决策表、§10 真信号的 AI 专属落点。做非 AI 功能可略;做 AI 功能缺任一问,PRD 不完整。

## 何时用 / 不用

- **用**:任何「一旦拍板代价大 + 要交给别人实现」的 feature。尤其当用户强调「决策点都要覆盖」「直给研发」「产品要读懂」时。
- **不用**:一次性小改(判断力直接做)、纯挑假设(用 `red-team-prd` 更轻)、纯拍板前对抗评审(用 `devils-advocate`)。本 skill 的增量是**决策全覆盖 + 零推断实现卷 + 两层验收**。

## 三条判据(交付前必过,按优先级)

1. **可转述(第一)**:PM **合上文档**,能凭记忆向外行讲清「解决什么问题 / 关键取舍 / 现在什么状态」?讲不清 → §2 概念或 §5 策略不够抓人,回去补。这条比下面两条都重要——文档全但讲不清,等于没做。
2. **决策可追**:每个影响架构的选择,是否都在 §12 有一行,带「为什么 + 否决的备选 + 定死/可复议」?尤其检查:AI 隐性做的取舍,有没有被逆向逼出来?
3. **研发零推断**:没有项目背景的研发读全篇,有没有任何一处要他「自己决定」?有 → 那个决策点没进 §12,或实现卷不够细。

## 八段式骨架(顺序即认知路径)

按 `references/template.md` 填空。每段的职责:

| 段 | 职责 | 常见漏 |
|---|---|---|
| 0 · TL;DR + 使用契约 | 一页版 + 「这份文档谁读、怎么用、哪些能动」 | 多数 PRD 没有使用契约,研发不知道边界 |
| 1 · 问题与背景 | **用户故事开场**,不是功能开场 | 一上来讲方案,读者不知道为谁解决什么 |
| 2 · 核心概念 | 建立词汇表,后文都用它 | 术语现编现用,读者对不上 |
| 3 · 系统流程 | **必配两图(mermaid)**:架构图谱(静态:组件/进程/表与边界)+ 数据 flow(动态:一次请求/一条数据怎么走完,时序图);文字流程围绕图展开 | 只有文字没有图;或只有静态架构没有动态旅程(反之亦漏) |
| 4 · 机制详解 | 关键子流程逐个拆 | 藏在实现里,产品看不到 |
| 5 · 设计策略与释疑 ★ | **疑问 → 决断 → 不这么做会怎样** | 只写「做什么」不写「为什么不那样」——本 skill 最出彩、最防后人改坏的一段 |
| 6–9 · 实现卷 | DDL + **字段词典**(逐字段:类型/含义与取值/谁写/谁读)/ API 完整契约 / 函数签名 / 按文件落点 / prompt 全文 | 粒度不够,研发要问一堆;只贴 DDL 没有字段词典,数据血缘(谁写谁读)读不出来 |
| 10 · 验收用例 | 每条带「层 + 可判定断言」,对齐 verify | 只写「要有测试」不写「测什么」 |
| 11 · 切片里程碑 | 线性推进,每片独立可验可止损 | 一个大爆炸,没法增量交付 |
| 12 · 决策登记表 ★ | 全决策点,每条「拍板/为什么/否决的备选/定死\|可复议」 | 决策散在正文,没法一眼看全盘、没法知道哪些能动 |

★ 两段是本 skill 相对普通 PRD 的核心增量。**§5 和 §12 缺任何一个,就退化成普通 PRD。**

## 两个必须做对的机制

### 决策登记表(§12)——借自 ADR

每个决策一行,五列缺一不可:

- **决策点** / **拍板**(选了什么)/ **为什么 + 否决的备选**(为什么不走另一条路)/ **状态**
- 状态只有两种:`定死`(研发不得改,多是防编造/防回潮硬约束)、`可复议`(已给默认值,owner 事后可调,**但不阻塞现在开发**)
- 按产品关心的维度**分组**(身份隐私 / 存储边界 / 审核分级 / 机制 / 工程运维 / 合规),让产品人能按主题读

这解决两个千年难题:研发不知道「哪些能动」(状态位解决),后人不知道「为什么不那样做」(否决的备选解决)。

### 设计策略释疑(§5)——每条一个反例

格式固定:**一个真实疑问 → 一句话决断 → 「不这么做会怎样」的具体反例**。反例不是吓唬,是把「这个约束为什么是硬的」讲到读者能自己推。写不出反例的「策略」,说明它其实不是决策、只是描述,应移进实现卷。

## 流程(尤其当 AI 已经把方案/实现做完时)

0. **逆向审讯取舍**(AI 已实现时的第一步,治「讲不清」的根):让实现方(AI 或代码)交代——哪些地方做了取舍?被否决的备选是什么?为什么?现状里哪些 passing、哪些 in_progress、哪些没部署?把这些答案当 §5/§12/§11 的原料。**跳过这步,PRD 必漏一半决策、且现状会写成计划。**
1. **定读者与目标**:谁读(PM 转述给谁 / 研发 / owner 评审)?写进使用契约。第一读者通常是「PM 自己要拿去讲」。
2. **先建概念(§2)再讲流程(§3)**:没有词汇表,后文全是黑话,PM 也转述不出。
3. **把散落的决策收拢进 §12**:遍历 §3/§4/§5/§9,凡「本可以那样但选了这样」「默认值是 X」「不做 Y」,都抓一行进决策表——决策全覆盖的机械动作。
4. **策略配反例(§5)**:每条决策问「不这么做会怎样」,答得出→升级成策略,答不出→降级成实现细节。
5. **现状锚定(§11 + 全文「现状」措辞)**:标现状前先回读代码/verify;passing/in_progress/未部署诚实分开。不拿方案描述当现状。
6. **实现卷做到零推断(§6–9)**:API 列到请求/响应/错误码/内部步骤;函数列到签名+语义;按文件列落点;prompt 给全文。
7. **验收对齐 verify(§10)**:每条标层(单测/e2e/真信号)+ 可判定断言;passing 闸必须含真信号。
8. **过转述测试 + `references/checklist.md`**:合上文档能讲清三件事?过不了回补概念/策略。

## 不断打造这个技能(迭代纪律)

这是用户要长期养的 skill。每次用完做一次回看,把新学到的沉淀回来:

- 写 PRD 时发现「研发还是问了某个问题」→ 说明某段模板漏了一类信息,补进 `references/template.md`。
- 发现某类决策反复出现(如「本地 vs 外采」「同步 vs 异步」)→ 抽成 `references/` 里的决策清单备查。
- 发现某段职责判据不好用 → 改本文件的判据表。
- 版本化记账:大改动在 `references/CHANGELOG.md` 追一行(日期 + 改了什么 + 为什么)。

skill 自身也走「求简先于求全」:模板别膨胀成填不完的表,只保留每次都真用到的段。加一段前先问「上次没有它,PRD 塌了吗」。

## 产出必带件

- **artifact 阅读视图**：md 落 `docs/` 为事实源,artifact 渲染 mermaid,同一 PRD 迭代更新同一链接。
- **artifact 必须内联 `references/artifact-mermaid-zoom.html` 片段**：pre.mermaid 点击 → lightbox,+/− 按钮 + 滚轮缩放 + 适应宽度 + Esc 关闭,纯 vanilla JS 过 CSP,角标提示「🔍 点击放大」。宽 mermaid 图在 artifact 里会被压缩到不可读,出厂自带这个片段,不等 owner 再提。
