# Agent 定位分析

**通用委托不存在——委托只能针对具体岗位。** 一个能力很强却没有岗位的 agent 是能力包：
你说什么它做什么，你不说它就停。

这一步接在市场定位之后。lenny-skills 的 `positioning` 回答“在市场里跟谁比、凭什么赢、卖给谁”，
对所有产品都适用；本 skill 回答另一个问题：**这个 agent 在产品形态上是岗位还是能力包**，只适用于 agent 产品。
两步都要做，先做通用的。

四个已上线产品的对照见 [CASES.md](CASES.md)（Claude Code / Cowork / Claude Tag / Grok Bot，
两个独立来源）。

## 第 0 问：任务形状，先于一切

任务时长是场景给的，不是设计者选的。它决定要不要委托。

```
时长 < 人能持续盯的时间 → 人在场 → 在场频率是设计选择
时长 > 人能持续盯的时间 → 人必然不在 → 判断权与记忆必须同时翻
```

| 时长 | 人 | 该建什么 |
|---|---|---|
| 秒/分钟级 | 盯着 | 速度与交互。委托机制会闲置 |
| 小时级 | 当天回来 | 完成回执 + 进度可见 |
| 天/周级 | 长期不在 | 全套：判断权、记忆三问、闸门、回执、无人值守闸 |

**同一产品内，不同时长的任务属于不同岗位。** 混装会让整体退化到最浅的那一档。

总时长与产出节奏要分开看：中途持续有产出 → 要害是**打扰节奏**（病叫淹没）；
最后才有产出 → 要害是**进度可见**（病叫失联）。

## 委托什么：在场，还是判断

任务形状决定**要不要**委托；这一节决定委托的是**哪一类**。两类的设计要点相反，
弄错方向的代价是整套设计作废。

**这是三个维度，不是三选一。** 一个岗位在三条轴上各有取值——
实测七个在跑的 bot，没有一个是纯类型，三维都高的那个（收件箱秘书）说明书最难写。

| 维度 | 它替你做什么 | 价值来自 | 该怎么设计 |
|---|---|---|---|
| **判断** | 决定做什么 | judgment | 高：给它否决权，配误否率<br>低：只做执行，不给裁量 |
| **在场** | 一直在那儿 | **availability** | 高：要 routine + 无人值守闸<br>**判断权越窄越安全**——自由发挥是风险不是能力 |
| **分诊** | 决定什么值得你看 | **议程权** | 高：打扰节奏 + **可枚举的升级白名单**<br>把最难的判断变成一张清单 |

| | 判断轴高 | 在场轴高 | 分诊轴高 |
|---|---|---|---|
| 记忆需求 | 跨对象常驻 | 会话级够用 | **跨任务状态**（派出去的活干完没） |
| 核心风险 | 决策错了（常不可见） | **说错话**（尤其承诺性信息） | 该报的没报 / 不该报的淹没你 |
| 闸门重点 | 限制它能决定什么 | **限制它能说什么**（内容白名单） | 限制它什么时候能打断你 |
| outcome | 产出份额 + 误否率 | 覆盖率 + 转化率 | **需要你拍板的条数** |

**在场型岗位的理想闸门位置**：拦住的正是它不该有的自由，因此**不吃判断权**。
比如「薪资只允许从配置逐字读出、禁止生成」——这条闸不降低它的价值，反而是它成立的前提。

## 三格尺

```
落点   （终端 + 用户）      它在哪工作、给谁
在场   （人数 × 频率）      几个人看着、多久不在一次
委托权 （判断权 × 记忆）    它能决定什么、记住什么
```

落点必须过三条硬条件：**有边界**（说得清里外）、**可授权**（用户能一次交出去且知道交了什么）、
**可撤销**（干错了能看见能回滚）。文件夹三条全中，浏览器三条全缺。

**判断权与记忆是一对耦合项，不是两格。** 只翻判断权，它主动做事却学不会规矩——同一个错犯一百遍；
只翻记忆，它很懂你，但你不打开就一次不动。

```
它能做多深      = 判断权 × 记忆
你敢让它做多深  = 判断权 × 记忆 × 可审计性
```

每格的完整定义——半格陷阱（cron 与名单驱动交出了调度权、留下了判断权）、规则 vs 判断、
记忆三问（怎么记 / 记多久 / 怎么忘）、记忆与判断权为何是不同种类——见 [DIALS.md](DIALS.md)。

## 判定：岗位还是能力包

**容器带不带自己的记忆和判断权？**

| | 容器 | 自己的记忆 | 判断权 | 判定 |
|---|---|---|---|---|
| Grok Bot | Bot | 有，每 Bot 一份 | 有，routine | **岗位** |
| Claude Tag | Slack 频道 | 有，频道级常驻 | 有，自己判断何时插话 | **岗位** |
| Cowork | plugin | 无 | 无 | 能力包 |

plugin（skills + commands + MCP + sub-agents）只填了岗位说明书六栏里的**职责范围**一栏。
装了 legal plugin，Claude 会审合同；但没有人对审合同这件事负责。

**不看名字，只查这两样**——GPT、agent、助手、智能体、数字员工，一律适用。

## 什么算新产品

```
用户群变，或任一参数翻转  → 新产品     （Cowork 换人群；Tag 翻参数）
只有落点变，人群与参数不变 → 渠道扩展   （Cowork 上 web）
三者都不变，只加能力      → 迭代       （Cowork 加 11 个角色 plugin）
```

## 诊断已有产品

按依赖顺序检查五个位置——**上游缺了，下游就建不起来**。展开见 [DIAGNOSE.md](DIAGNOSE.md)。

```
1. 授予动作  有没有「用户交给它一条规则」的时刻？没有 → 只是内置规则，不是委托
2. 句柄      要暂停它，暂停的是哪个对象？没有 → 无从治理，也就不敢长期开着
3. 判断一    该不该动 —— 那个决策点读的是什么？元数据触发 = 规则不是判断
4. 判断二    该不该说 / 该不该否 —— 这一步存在吗？缺 → 它省手不省判断力
5. 记忆      这次的结论会改变下次的行为吗？不会 → 每次从零开始
```

**诊断必须说出哪一样是好的。** 说不出好的，修法会往回退——把「判断权」误判为缺失，
会导向「收回它的否决权、让它全推给我」，产品退回省手。

## 收口

**做完 = 三格都有具体取值，且「岗位 / 能力包」的判定有明确依据。**
判定为能力包时，说清缺的是记忆、判断权，还是两者都缺。
